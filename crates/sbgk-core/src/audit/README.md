# Audit storage

`AuditState` stores swarm records and the growing audit ontology separately from the fixed engine ontology. The graph builder is a separate internal role, outside the external swarm. This module implements storage and validation, not a running swarm or a model adapter.

## Opening a session

Use `AuditState::create` with explicit document IDs, `create_from_docs` for a set of supplied files, or `create_from_manifest` with the original manifest bytes and selected `(repository_relative_path, raw_bytes)` pairs. The manifest loader checks the pinned repository/commit/path/raw-SHA256 identity and excludes auxiliary Markdown and non-report files. Lexical revision mentions remain unresolved metadata.

`AuditState::new` provides read-only inspection. Mutations require a durable journal. `create` never overwrites an existing file; `open` validates and replays it under an exclusive writer lock.

## Dispatcher integration

- Authenticate the subject and authorize its role on the server. Strings such as `owner`, `builder` and `kernel` are provenance within this trusted in-process interface, not credentials.
- Call `submit_scoped_records_id` with a stable transport submission ID, authenticated actor, directive, document/range scope, exact issued record IDs and the result lines. References may use issued records and the actor's previously accepted prefix for that directive. Observations must match a unique exact byte span inside an issued range. The compatibility `submit_records_id` checks document provenance instead of exact issued record capabilities.
- On partial failure, retain the accepted prefix and submit only the repaired suffix under a new submission ID. Exact retries return the durable original receipt before fresh context validation; reuse of an ID with different content fails. Locals are scoped by actor/directive and survive recovery.
- Call `submit_operations_id` for one coordinator operation prefix, its receipt and an optional processed-cursor checkpoint. Its checkpoint is `{key, from, to, context}`; `from` must equal the durable cursor and `to` must lie within the ingest head. Empty successful batches can acknowledge a checkpoint. Check `error` and `checkpointed` in the returned result. A failed suffix keeps the accepted operation prefix but does not advance the checkpoint.
- Restore completed tasks and receipts from durable coordinator checkpoints. Active leases, issued cards, RPC routing and retry lookup before ephemeral-card validation belong to the dispatcher. The builder/directive skeleton does not yet use all these APIs.

There are three distinct axes: source `stance`, current structural `is_grounded`, and established `is_answer_support`. A relation can remain structurally grounded after rejection while losing answer support. `link_usable` also requires active proposal and verifier evidence. Do not treat record existence, a stored `Accepted` label, or an old `done` as current task completion. Check support and all task conditions at the same cutoff; terminal unknown remains a separate outcome.

## Ontology and records

The six strict record shapes are embedded in `schema.json`; runtime validation also checks calendar integers, UTF-8 byte limits and the documented schema extensions. Record IDs commit to resolved content, actor, directive and a per-directive ordinal. Renaming a local ID or inserting another directive does not rename a record.

New concepts are provisional. Status changes require a separately authorized coordinator decision. `same_as` and `duplicate_of` are explicit proposals, never inferred identity from equal names. Record relations must have a declared record-to-record signature; non-rejected `supersedes` links must be acyclic, including reactivation.

Source observations bind legacy engine evidence to a specific document version. Document updates and revocation invalidate dependent support without rewriting historical records. Manifest-derived IDs are immutable; a changed source needs its new identity. Agent-supplied valid dates and kernel ingest order are labeled separately; publication dates are not inferred from filenames.

## Rules 4 (0.3.0): a journal that takes its sources as they come

A genesis names the rules its journal runs under. A new journal names `r2r-audit-rules/4`; a journal that names `r2r-audit-rules/3` is replayed, and written on, under the rules of 0.2 (`AuditState::set_rules_version` starts a run under them, for the tools of 0.2). The journal format, the root format and the seal format are the same for both.

Rules 4 are rules 3 with these additions (`state/stream.rs`, read by `vsc.rs`):

- **A run may start without a document** and take every source later (`put_document`; `sbgk audit-stream`, `audit-serve --empty-start` with the owner's `audit_put_document`). This held under rules 3 too, for a journal of supplied documents; 0.3.0 opens it on the command line and in the server. Sources are UTF-8 text. Under rules 4 the name of a source that comes later has the bound of a name the journal starts with (512 bytes): the key of the task that reads it holds the name.
- **A claim may rest on a claim.** The rule stays AND: a claim stands while every ground of it stands. The grounds of a relation and of a hypothesis stay observations.
- **A context checkpoint** is the checkpoint command with the key `vsc:checkpoint:<epoch>`, a frame of its own: the records an agent keeps across a compaction of its context, the sources they rest on with the SHA-256 of their bytes, and the source that holds the raw context. Its epochs count from 1 by one, it is written once, and it lists records that are active when it is written (a record that fell, was withdrawn or was replaced is refused by name) and sources that exist. It is never the checkpoint or an operation of a batch. `read_active_checkpoint` gives back only its records that are active now. A journal of rules 3 has no context checkpoint: a checkpoint with such a key is any checkpoint there, and the reads do not give it out as one.
- **A planned change is not a withdrawal.** A relation `supersedes` from the new record to the old one leaves the old record standing and no longer current (`SUPERSEDED`); nothing that rested on it falls. A withdrawal (`revoke`, `revoke_text`, which may name the document that is its reason, `reason_source_id`) makes the quote `WITHDRAWN` and what rested on it `AFFECTED_BY_EVIDENCE_CHANGE`. A replacement that falls replaces nothing: the old record is the current one again.
- **The key of a claim is its `subject`, compared as the exact string, and its value its `object`.** `vsc::key` reads the value a key has now; `vsc::keys` lists the keys, the keys whose active claims say different values (`VALUE_CONFLICT`) and the required keys no active claim says (`MISSING_REQUIRED_KEY`). These are projections over the journal: the kernel refuses no record for them.
- **A question may name the record it is about** (`about_record`): an address in its body, not a ground.

The flags of the records after a put document are computed from the flags before it, as after a submit or a withdrawal (0.2.5): the quotes of the document are looked at again, and what rests on a quote whose flags changed. In the tests, and in a build with the feature `audit-root-verify`, every such update is compared with a whole pass over the records.

A source that gets other bytes is read again (`directives/sources.rs`, a decision of the dispatcher and no rule of the journal): the completion checkpoint of a reading of a document that was ever given other bytes names the version it was issued on (`source_version`), and the reading is over for that version alone, for the live dispatcher and for one recovered from the journal. The checkpoints of a document that keeps the bytes it came with are what 0.2 wrote.

A writer without a dispatcher (`sbgk audit-stream submit`) names in the scope of a submission the documents its lines need: those they quote and those under every earlier record they name (`AuditState::scope_of_lines`).

## A cut of several journals and the observation report (0.3.1)

Two readings over sealed journals, neither of which adds a field to a frame or a rule to the journal. Their formats are fixed in `verifier/spec/SPEC_CUT_AND_BUNDLE_v1.md` and `verifier/spec/SPEC_OBSERVATION_REPORT_v1.md`, and the independent verifier checks a bundle and recomputes a report without this code.

- **An export** (`cut.rs`, `sbgk audit-cut export`) is a text document made from one journal at one of its seals: the claims that stand there, or those named, each as one line with the claims and the quotes it rests on. Another party puts it into its own journal as an ordinary document and quotes it byte for byte. A record that is no claim, or does not stand at that seal, is refused.
- **A cut** (`sbgk audit-cut manifest`) binds the journals of a bundle at named seals, the exports and their deliveries. The manifest is made of what the journals show: an export file that is not the export made of its records is refused, and the deliveries are found, never typed: every document a journal took in with the exact bytes of an export, by its genesis record or by a `put_document` frame of its own. A batch that brings such bytes in cannot be declared, and the cut is refused. Whether a bundle passes, and why not, is the independent verifier's to say: the command names no failure of a bundle. A cut delivers no withdrawal: an operator's process does.
- **The observation report** (`observation.rs`, `sbgk audit-observation`) gives, for every claim of one journal up to a seal or of the journals of a cut, three separate axes: support (does it stand on its evidence, and on which withdrawn or replaced quotes it fell), dispute (is it contradicted by a standing claim) and time (has a standing later claim replaced it); with them who made the claim and on which bytes, what it rests on within its journal and across, the questions about it and the conflicting values of exact keys; and two counts of frames, the answers the kernel refused and the answers sent to a task already closed. The axes are never merged into one status, and the debt counters are never summed. A report is of a checked input. A manifest someone else wrote is read as it says (`cut::read`): whether a journal is closed at its seal, which journal an export was made from and which export a delivery brought are the manifest's words, checked and never looked up again; the documents of every genesis record must be in the journal's folder, as a check from outside needs them; and a cut that fails the bundle check gets no report, with the level of the check it fails. What the command admits is what the independent verifier admits, no more and no less. The rule of the time axis is the report's own: `quality/stale.rs` and the exact-key reads answer a later state by rules of their own.

A journal's part in a cut ends with the seal the cut names, and with the close right after it where the cut says the journal is closed: the frames after it are not replayed. A made manifest says closed when the close follows the seal; a given one may name the journal open at that seal though the file goes on. Where a seal is named (`--seal`, `--at`, a manifest), the part is read as a file of its own (`Journal::read_part`): the frames after it are not validated either, so a frame damaged after the part does not take the part away. With no seal named the command takes the last seal of the file itself, and the whole file is then its input: it answers only where `audit-verify` verifies that file. A torn tail is refused with status `TORN_TAIL`, and a frame after the last seal that the kernel refuses ends the command (`Part::rest_replays`); either refusal says how to name the seal. Sound frames after the last seal are counted in the answer.

An output is written over no file of its input. The inputs are: for an export, the journal, the list of its records and the documents beside the journal (`<folder of the journal>/docs`); for a manifest, every journal and every export of the bundle and every file of every `<journal>/docs`; for the report of a journal, the journal, every file of `--docs` and the documents beside the journal; for the report of a bundle, the manifest and the same files of the bundle. Documents kept anywhere else are not known to a command that is not given them.

The report of one journal (`--wal`) is of the journal with its documents, up to the seal: a close after the seal is no part of that input. The documents of the genesis record are asked for in the folder of `--docs`, each known by its bytes whatever its file is called; a document that came by a `put_document` frame is in its frame. Without them the journal cannot be checked from outside, and gets no report. One replay of a part keeps who stood at every seal its exports name.

## Durability and commitments

One `sbgk-session-log/2` frame commits the staged engine changes, audit changes, request/outcome receipt and coordinator checkpoint. Storage writes and synchronizes the frame before publishing the new in-memory state. A write/sync failure poisons that writer; reopen and retry the same submission ID to resolve an uncertain outcome.

Frames have a version, monotonic sequence, previous hash and canonical JSON payload. Recovery checks framing/hash continuity, then reexecutes commands and compares outcomes and both post-roots before repairing an unterminated final tail. A malformed complete frame or semantic divergence fails without tail repair. The reader rejects duplicate fields and noncanonical encodings. There is a 64 MiB frame limit and a 1 GiB log limit.

`audit_root` commits records/provenance, source identities, ontology, mappings, links/decisions, receipts and checkpoints. `engine_root` remains the engine commitment. `session_root = SHA256("R2R-AUDIT-SESSION/1" || engine_root || audit_root)` binds both. `wal_head` separately commits journal order. Authenticating a historical head requires an externally trusted checkpoint: a hash chain alone cannot detect replacement by a rehashed history or truncation to a valid prefix.

The old engine WAL, `sbgk-session-log/1` and binary `.sbgk` container v1 are unchanged. The old journal reader refuses v2. An exported engine container contains only the engine component; it does not persist audit records, the growing ontology, receipts or task state. Retain the outer v2 journal for full recovery. No implicit migration is provided.

Transactions currently reconstruct the engine from its WAL when staging. This conservative prototype has O(WAL) staging cost and does not demonstrate throughput for hundreds or thousands of workers. Replication, network services and power-loss behavior across filesystems need separate validation.
